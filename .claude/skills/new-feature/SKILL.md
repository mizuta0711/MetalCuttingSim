# 新規設計書の作成

機能開発・改修・バグ修正に対応する設計書を作成する。

## 手順

### Step 1: 変更の性質と規模をユーザーに確認

1. **変更の性質**（AI が推測して提示、ユーザー承認）:
   - 新規追加: 新しい機能を作る
   - 改修: 既存機能を変更する
   - バグ修正: 既存コードの不具合を直す

2. **変更規模**（AI が推測して提示、ユーザー承認）:
   - S: 1〜2 ファイル、既存システムの微調整
   - M: 3〜10 ファイル、既存パターンに沿った追加
   - L: 新しいゲームシステム追加、複数シーン変更、Prefab 設計変更

判定ルール:
- 新しい MonoBehaviour システムを追加する場合は L 寄りで提示
- 迷わなければ L 寄りで提示する

**提示例**:
```
指示内容から以下と判断します:
- 変更の性質: 新規追加（切削シミュレーションシステム）
- 変更規模: L（新規 MonoBehaviour 2 クラス、既存システムとの連携必要）

この判定で進めてよいですか？
```

### Step 2: テンプレートをコピーして設計書を作成

1. テンプレートを読み込む: `docs/features/TEMPLATE.md`
2. 以下の命名規則でファイルを作成:
   - パス: `docs/features/yyyymmdd_$ARGUMENTS.md`
   - 日付は本日の日付（yyyymmdd 形式）
3. メタ情報を埋める:
   - 全体ステータス: `🔵 設計中`
   - 変更の性質・規模: Step 1 で確定した値
   - Stage 1 ステータス:
     - L 規模: `🔵 記入中`
     - M 規模: `⚪ 不要`
     - S 規模: 設計書自体を省略してよい

### Step 3: ユーザーへの報告

- 作成したファイルパス
- 変更の性質と規模
- **次のアクション**:
  - L 規模: Stage 1（ゲーム・システム設計）を記入後、`/design-review feature` でレビュー
  - M 規模: Stage 2（技術設計）を記入後、実装へ

## テンプレートが見つからない場合

`docs/features/TEMPLATE.md` が存在しない場合は最低限の構造で作成:

```markdown
# $ARGUMENTS

## メタ情報
| 項目 | 内容 |
|------|------|
| 全体ステータス | 🔵 設計中 |
| 変更の性質 | {新規追加 / 改修 / バグ修正} |
| 変更規模 | {S / M / L} |
| Stage 1 | 🔵 記入中 or ⚪ 不要 |
| Stage 2 | ⚪ 未着手 |
| 作成日 | {本日の日付} |

## 1. 概要
（背景・目的・方針を記載）

## 2. タスク一覧
| # | タスク | ステータス | 備考 |
|---|--------|-----------|------|

## 3. ゲーム・システム設計（Stage 1）
（L 規模のみ記入）

## 4. 技術設計（Stage 2）

## 改訂履歴
| 版数 | 日付 | コミット | 内容 |
|------|------|---------|------|
| 1.0 | {本日の日付} | (未確定) | 初版作成 |
```
