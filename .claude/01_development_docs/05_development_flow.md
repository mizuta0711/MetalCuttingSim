# 開発フローと規模判定

**変更規模判定**と **S/M/L 開発フロー**の詳細仕様。
CLAUDE.md の「設計・実装フロー」「バグ修正の原則」から参照される詳細ドキュメント。

---

## 1. 規模判定の詳細

### 1-1. 基準表（5軸）

| 観点 | S | M | L |
|------|---|---|---|
| 変更ファイル数 | 1〜2 | 3〜10 | 10超 または広範囲 |
| 新規 MonoBehaviour | なし | 既存パターンに沿った 1〜2 | 新システム追加 or 複数 |
| Prefab・シーン変更 | なし | 既存 Prefab の修正のみ | 新規 Prefab 追加、シーン構成変更 |
| プレイヤー体験変更 | なし（既存挙動維持） | 限定的（1システム内） | ゲームループ・難易度・フロー全体 |
| 設計書更新 | 不要 | 必要 | 必要（複数種類） |

#### 判定ルール

1. **最も該当する項目が多い規模を採用**
2. **1つでも L 相当の項目があれば L に引き上げる**
3. **新しいゲームシステムを追加する場合は自動的に L 扱い**（2段階設計が必要なため）

### 1-2. 判定プロセス

**AI が推測 → ユーザーが承認** の2ステップ。

```
1. ユーザーが作業を依頼
   例: 「切削シミュレーション機能を追加して」

2. メインClaude が指示内容と影響範囲から S/M/L を推測して提示
   例: 「これは L 規模と判断します。
         CuttingManager クラスを新規追加、
         MaterialSettingsSO の設計、
         GameScene への組み込みで複数ファイル・複数システムに影響します。
         進めてよいですか？」

3. ユーザーが承認 or 修正
   例: 「OK、L で進めて」または「簡単な試作から M で」

4. 承認された規模でフローに入る
```

### 1-3. AI バイアス補正ルール

AI が「楽な方（S 寄り）」に判定する傾向を抑制するため:

- **判定に迷ったら L 寄りで提示する**
- 新規 MonoBehaviour を追加する場合は基本 L で提示する
- **過小見積もりより過大見積もりの方が安全**

### 1-4. スコープ拡大時の再判定ルール

実装中に「予想より大きな変更になりそう」と気づいた場合の対応:

| 気づくタイミング | 対応 |
|----------------|------|
| 着手前 | 即停止して再判定 |
| フェーズ実行中 | **現フェーズを完了**させ、フェーズ完了時の報告で再判定を提案 |
| 破壊的変更（既存 Prefab 構造・ScriptableObject 型変更）が必要と判明 | **即停止** |

### 1-5. 補助軸（変更の性質）

規模 (S/M/L) とは独立した軸として、変更の性質を意識する:

| 区分 | 意識すべき点 |
|------|-------------|
| 新規追加 | 既存パターン（クラス設計・依存関係）を先に確認してから設計する |
| 改修 | 「何を変えるか・何を変えないか」の境界を明示する。既存挙動を壊さない保証をレビュー観点に含める |
| バグ修正 | 根本原因を確定してから修正する（§3 参照）。症状に飛びつかない |

## 2. S/M/L フローの詳細

### 2-1. S 規模の詳細（軽微な変更）

対象:
- ScriptableObject のパラメータ調整
- テキスト・定数修正、1ファイル程度の修正
- 軽微なバグ修正（null チェック漏れ、オフセット調整等）

フロー:
```
実装 → /build-check → コミット → /done
```

省略する工程:
- 設計書作成（不要）
- 設計レビュー（不要）
- コードレビュー（不要）
- `/update-docs`（設計書変更なし）

### 2-2. M 規模の詳細（機能追加・複数ファイル変更）

**前提**: 新規ゲームシステムを含まないこと。新システムを伴う場合は L に引き上げる。

対象:
- 既存システムへの機能追加（既存クラスにメソッド・状態追加等）
- 複数ファイルにまたがる改修（ゲームループ変更なし）
- 中規模のバグ修正（複数クラスにまたがる不具合等）

フロー:
```
設計 → 実装 → /code-review → /build-check → /update-docs → コミット → /done → プッシュ
```

#### M 規模での設計書

- 機能設計書は **1段階設計**（「3. ゲーム・システム設計（Stage 1）」は `⚪ 不要` でスキップ）
- 「4. 技術設計（Stage 2）」のみ記入

#### 注意事項

- Unity 動作確認は Claude が直接実行できない。実装後に **Unity Editor で手動確認**すること
- `/update-docs` で全タスク完了を検知すると、自動で sync-check → `completed/` 移動が実行される
- レビュー前にコミットしない

### 2-3. L 規模の詳細（新システム追加・大規模変更）

対象:
- 新しいゲームシステム追加（新規 MonoBehaviour 群、新 Prefab 設計）
- プレイヤー体験の大幅変更（ゲームループ変更、難易度設計変更）
- 複数シーンにまたがる変更
- 大規模リファクタリング
- アーキテクチャレベルのバグ修正

フロー（2段階設計必須）:
```
設計 Stage 1（ゲーム・システム設計）
  → /design-review feature (code-reviewer + game-designer 並列実行)
  → ユーザー承認
設計 Stage 2（技術設計）
  → /design-review tech (code-reviewer)
  → 実装 → /code-review → /build-check → /update-docs → コミット → /done → プッシュ
```

### 2-4. プッシュ前の共通フロー

```
/pre-push-check → プッシュ
```

### 2-5. フロー共通ルール

- **レビュー前にコミットしない**（M, L の場合）
- Unity 動作確認は常に手動。実装後に Unity Editor で PlayMode テストを行うこと
- 一度に編集するファイルは最大5ファイル

## 3. バグ修正の詳細

### 3-1. フロー順序（原因特定 → 規模判定 → 設計書）

**症状だけで規模を決めない**。原因特定後に判定する。

```
1. バグ発見（症状の報告）
   ↓
2. 原因特定フェーズ（対話的、設計書なし）
   - Unity Console のエラーメッセージ全文確認
   - Debug.Log 追加 or 最小再現手順で原因を確定
   - 「何が原因だと考えたか」を短く示す（仮説の先行共有）
   ↓
3. 規模判定フェーズ
   - 原因が確定した段階で、修正に必要な変更範囲を見積もる
   - AI が S/M/L を推測・提示 → ユーザー承認
   ↓
4. フロー選択
   ├─ S: 直接修正 → /build-check → コミット → /done
   ├─ M: 軽量な設計書作成 → /code-review → /build-check → /update-docs → コミット → /done
   └─ L: 通常の設計書作成（2段階設計）→ 以降 L フローと同じ
```

### 3-2. M/L 規模バグの設計書の書き方

既存の機能設計書テンプレート（`docs/features/TEMPLATE.md`）をそのまま使う:

| 機能設計書のセクション | バグ修正時の内容 |
|---------------------|-----------------|
| 1. 概要 > 背景 | 問題の発見経緯・症状・再現手順 |
| 1. 概要 > 方針 | 根本原因の分析・修正アプローチ |
| 4. 技術設計 | 修正内容・影響範囲・再発防止策 |
| 動作確認計画 | 修正箇所の Unity Editor 動作確認項目 |

## 4. 2段階設計の詳細（L 規模）

### 4-1. Stage 1: ゲーム・システム設計

**目的**: 「何を作るか」「なぜ作るか」「どんな体験を提供するか」を確定する

**記入内容**:
- 対象システム・シーンの一覧
- プレイヤー体験・ゲームループへの影響
- 既存システムとの関係・依存
- 受け入れ条件（「完成」の定義）

**レビュー**: `/design-review feature`
- **code-reviewer**: 設計書間の整合性、MonoBehaviour 責務分離、依存関係の妥当性
- **game-designer**: ゲームデザイン妥当性（コアループ、プレイヤー体験、難易度バランス）

**承認ゲート**: ユーザー承認で Stage 2 に進む

### 4-2. Stage 2: 技術設計

**目的**: 「どう作るか」を確定する

**記入内容**:
- 追加・変更クラス一覧（種別・配置先・役割）
- クラスの public インターフェース設計
- ScriptableObject パラメータ設計
- Prefab・シーン変更内容
- 依存関係・注意事項

**レビュー**: `/design-review tech`
- **code-reviewer**: クラス設計の技術的妥当性、Unity API の適正使用、パフォーマンス懸念

**承認後**: 実装フェーズへ

### 4-3. Stage 2 → Stage 1 戻り手順

Stage 2 記入中に技術制約で実現不可と判明した場合:

1. Stage 2 の記入を中断
2. 設計書メタ情報の「Stage 1 ステータス」を `🟡 再レビュー中` に戻す
3. 該当する Stage 1 セクションを修正
4. `/design-review feature` を再実行
5. ユーザー再承認
6. Stage 2 を再開

改訂履歴に「Stage 1 を再修正した版」として明記する。
