# コードレビュー＋指摘対応

## Step 1: レビュー対象の特定

`$ARGUMENTS` が指定されている場合はそのファイル/ディレクトリを対象。
未指定の場合は直近の未コミット変更を対象:

```bash
git diff --name-only
```

変更がない場合は直近1コミットの変更ファイル:

```bash
git diff --name-only HEAD~1
```

## Step 2: レビュー実施

変更内容に該当する項目のみチェックする（全項目を毎回チェックしない）。

### 常にチェック

- `namespace MetalCuttingSim` の宣言があるか
- クラス名とファイル名が一致しているか
- `Assets/Scripts/` の適切なサブフォルダに配置されているか

### MonoBehaviour を継承するクラス

- `GetComponent<T>()` が Update() 内で呼ばれていないか（Start() でキャッシュすること）
- `FindObjectOfType<T>()` / `FindFirstObjectByType<T>()` の多用がないか
- マジックナンバーがないか（ScriptableObject または `const` / `[SerializeField]` で定義）
- `Destroy()` 後の参照アクセスがないか

### ScriptableObject を使うクラス

- パラメータが適切に外出しされているか（ハードコードされていないか）
- `[CreateAssetMenu]` 属性が付いているか

### パフォーマンス

- Update() で重い処理（Physics 計算、文字列操作の多発等）が行われていないか
- コルーチンや UnityEvent で代替可能な定期処理が Update() に残っていないか

## Step 3: 結果をファイルに保存 + 報告

レビュー結果を `docs/reviews/YYYYMMDD_HHMMSS_code-review.md` に書き込む:

```markdown
# コードレビュー結果

- 実施日時: YYYY-MM-DD HH:MM
- 対象: （レビュー対象ファイル一覧）

## 指摘事項
| # | 重要度 | 場所 | 内容 | 対応状況 |
|---|--------|------|------|---------|
| 1 | 重要/中/低 | ファイル:行 | （指摘内容） | 修正済み/未対応 |

## 判定: ✅ 承認 / ⚠️ 条件付き承認 / ❌ 差し戻し
```

ユーザーには**判定・指摘件数・重要な指摘の概要**のみ報告する。

## Step 4: 指摘対応（自動修正）

重要度が「重要」の指摘で明確な修正方法がある場合は自動修正を行う。
修正後、レビュー結果ファイルの対応状況を「修正済み」に更新する。
修正が複雑な場合や判断が必要な場合は、修正案を提示してユーザーに確認を求める。
